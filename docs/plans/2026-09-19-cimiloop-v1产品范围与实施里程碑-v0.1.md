## 2026-09-29 适用性校准

当前约束以 [独立研发流程基线](../architecture/AI-Native软件研发流程-v0.1.md) 和 [统一模型与共享发布决策](2026-09-28-cimiloop-requirement-bug-unified-model-design.md) 为准。N1–N5 是价值流程与责任框架，M0–M5 是工程里程碑，两者不是一一对应的业务阶段。

单条需求可继续作为最小验证场景，但不能据此把 Release 限定为该需求的子对象。需求 / 缺陷共用台账、目标版本可选、澄清可平级拆分；实施可在隔离分支开展，集成与发布则是项目级共享流程。

范围与验收仍需补齐：多人 / 多需求共同纳入的固定快照、feature 集成、release 范围固定、共享测试环境切换及排队 / 在途覆盖保护、修复优先与安全剔除延期，以及逐需求完成判定。共享发布不自动要求引入组织账号、实时多人协作或大规模编排，也不表示这些能力已实现。

正文保留旧范围及里程碑拆解供参考。完整现行流程细则与实施计划尚待确认，不能从本轮提示推导字段、完整枚举、迁移或新的技术选型；下文旧“已确认”结论不恢复直接执行资格。

## 1. V1 产品定义

CimiLoop V1 是运行在开发者本机、首个 Agent Runtime 从 Claude Code 或 OpenCode 中选择的 Runtime-neutral Harness。它围绕一个 Change，把意图、计划、执行、独立评价、测试部署、生产发布、恢复与关闭组织为确定性的闭环。企业内部基于 OpenCode 二次开发的 cimicode 后续通过同一 Runtime Adapter 契约接入，不作为 V1 前置依赖。

V1 的成功不以“拥有多少 Agent、页面或 Adapter”为衡量标准，而以一条真实 Change 能否在异常、重启和人工决策下仍然可追踪地走完闭环为标准。

### 1.1 目标用户

- 主要用户：希望使用 Agent 完成真实软件变更，同时保留控制权和证据链的个人开发者；
- 次要用户：在单机环境验证 AI Native 研发流程的小型研发团队或技术负责人；
- 非目标用户：需要组织级账号、实时协作、多租户治理和大规模发布编排的企业团队。

### 1.2 V1 默认运行模式

- Embedded Solo Mode；
- 一个本地 Human Actor 可以显式承担多个责任角色；
- A1 监督自治等级；
- 本地 Kernel、SQLite、Local Files 和 Workbench；
- Claude Code 或 OpenCode Runtime（先落地一个）；
- Git / Local Workspace；
- File Knowledge；
- 复用已有 CI/CD、Artifact Registry 和 DevOps/Environment 能力。

## 2. V1 北极星验收闭环

V1 必须使用一个真实、可控的软件项目完成以下闭环。目标生产环境可以是专门用于验收的低风险真实环境，但部署必须产生可核对的外部副作用，不能完全由内存 Mock 代替。

```text
用户明确创建 Feature Change
→ Draft Change 与唯一 Change Owner
→ Agent 澄清并形成 Contract Candidate
→ Intent Owner 批准 Contract Version
→ Kernel 自动创建 Planning Work Item
→ Planner 形成 Plan 与 Task DAG
→ Technical Owner 批准 Plan Version
→ Kernel 创建 Ready Work Item
→ Claude Code/OpenCode Executor 在隔离 Worktree 实现
→ 固定 Source Snapshot 并构建 Artifact
→ 独立 Evaluator 形成 Claim / Evidence / Evaluation
→ Gate 允许测试部署
→ 同一 Artifact 部署测试环境并验证
→ 形成 Production Release Package
→ Release Owner 批准具体 Release
→ 同一 Artifact Digest 晋升生产
→ 完成即时验证
→ 完成受影响知识更新并形成 Evidence
→ Change Owner 关闭交付
→ 形成完整 Timeline、Decision、Evidence 与 Learning Candidate
```

### 2.1 主场景验收结果

主场景完成时必须能够回答：

- 谁在何时以什么角色批准了什么版本；
- 每个 Agent Run 获得了什么 Context、Capability 和权限；
- 哪个 Source Snapshot 产生了哪个 Artifact Digest；
- 哪些 Claim 被哪些 Evidence 支持；
- 测试与生产是否使用同一个 Artifact；
- 每次状态迁移由哪个 Gate Evaluation 支撑；
- 外部部署事实在哪里核对；
- Change 为何可以关闭，还有哪些残余风险与未观察 Outcome。
- 哪些产品、业务、技术或运维知识受到影响，由谁更新到哪个版本，是否仍存在已知陈旧知识。

## 3. 必须通过的异常验收场景

V1 不能只演示 happy path（正常路径）。以下异常路径全部属于发布门槛：

| 场景 | 必须表现 | 验收结果 |
|---|---|---|
| 独立评价失败 | Evaluator 产生 Refutes Evidence，Change 返回 Executing，创建 Repair Work Item | 旧失败保留；修复形成新 Artifact 并重新评价 |
| Artifact 改变 | 新 Digest 触发精确影响评估 | 绑定旧 Artifact 的测试与评价 Evidence 不再支撑新 Gate |
| Decision 过期 | 等待批准时 Contract、Artifact、Environment 或范围变化 | 原 Decision Request 过期，不能继续提交或复用旧批准 |
| 外部结果未知 | 部署调用超时或连接中断 | 停止盲重试，打开 Blocker，执行 Reconciliation 后再决定 |
| 生产验证失败 | 即时检查发现目标版本、健康或核心路径异常 | 执行预授权 Recovery；超范围时进入 AwaitingDecision |
| Kernel/进程重启 | 存在未完成 Run、Outbox 或 Deployment | 核对 Lease、Outbox 与外部状态，恢复调度且不重复副作用 |
| 权限/Policy 变化 | 进行中 Work Item 的权限或安全规则被撤销 | 禁止新操作，安全停止或请求新授权，历史保持不变 |
| Export/Import | 将完成和进行中的项目导出到隔离目标 | 保留 ID、版本、Event、Digest；运行时所有权不被错误激活 |

## 4. V1 范围分级

### 4.1 P0：V1 发布必须具备

#### Protocol 与 Kernel

- V1 核心对象、稳定 Internal ID、Typed Reference 与 Schema Version；
- Change 多维状态机、Transition、Gate、Decision 和 Event；
- Contract/Plan 独立业务版本与 Amendment；
- Current State、Event Ledger、Transactional Outbox 和幂等 Command；
- Aggregate Revision、Event Sequence、Lease 与 Resource Lock；
- Failure、Blocker、Feedback 和 Learning Candidate；
- Close、Archive、Cancel、Supersede、Recovery 和 Reconciliation 语义。

#### 角色与治理

- Project Owner、Change Owner、Intent Owner、Technical Owner、Release Owner；
- 本地 Human Actor、Agent Actor、acting role 与 Assignment；
- A1 模式下三项基础人工决策：Contract、Plan、Production Release；
- 普通风险角色重叠；高风险职责分离与受控 break-glass；
- 确定性 Project Policy 与 Policy Snapshot。

#### Workbench 与 Change Room

- Project Workbench 的 Attention Queue、Decision Inbox 和 Change 列表；
- 显式创建 Change；
- Change Room Current Focus、六阶段导航和下一动作；
- Contract、Plan/Task、Run、Evidence、Delivery 与 Activity 视图；
- 生命周期时间线与 Run 技术明细入口；
- 结构化 approve、request changes、reject 决策。

#### Context 与能力装配

- 不可变 Context Pack Manifest；
- 按 Role 提供最小必要上下文；
- File/Git/CimiLoop/Runtime/Test 来源；
- Capability Requirement、Provider Descriptor、Resolver 与 Run 级 Binding；
- Runtime、Model、Skill、Tool 和 Adapter 精确版本摘要；
- 能力缺失 Blocker 和权限交集校验。
- Knowledge Impact Assessment、Human/Agent Knowledge Task、External Reference 与知识更新 Evidence；

#### 执行与验证

- 默认一个 Change 一个隔离 Worktree；
- Kernel 下发 Work Item，首个 Claude Code/OpenCode Runtime 创建 Agent Run；
- Planner、Executor、Evaluator 独立角色 Session；
- 不可变 Source Snapshot、Artifact ID 与 Digest；
- Claim、Supports/Refutes/Inconclusive Evidence；
- Gate Requirement Set、独立 Evaluation 和 Evidence Package；
- Valid、Stale、Superseded 影响评估，以及完整性错误导致的 Invalid Evidence。

#### 交付与恢复

- build、deploy、status、verify、recover、reconcile Adapter 能力；
- 测试环境部署—验证—修复—重建循环；
- 测试到生产的同 Digest 晋升；
- Environment、Release、Deployment 分离；
- Release Owner 一次性生产授权；
- 生产即时验证；
- 未知结果核对和预授权 Recovery。

#### 存储与可移植性

- SQLite + Local Files；
- 逻辑 Store Port；
- 可重建 Read Model；
- Project Portable Export/Import；
- Import Staging、完整性校验和 Import Report；
- Solo→Team 迁移语义的自动化契约测试。

### 4.2 P1：允许在 V1 中简化

- Workbench 先使用列表，不要求完整 Lifecycle Board 拖拽交互；
- Change Profile 先重点验证 Feature、Bugfix、Incident，其他 Profile 使用统一基础状态机；
- Project Policy 使用代码或配置定义，不建设通用策略编辑器；
- 本地 Identity 使用轻量配置，不建设登录与组织目录；
- Artifact 可以由 Git、文件目录或现有 Registry 承载，不自建 Registry；
- DevOps Adapter 可以先接入一个真实 Pipeline/Environment；
- Notification 先使用 Workbench 内通知，桌面通知可选；
- Evidence Package 先采用 Manifest 与查询视图，不建设复杂报告设计器；
- Context 检索先使用精确文件、Git 和协议引用，不要求语义搜索。
- 飞书、Confluence 等外部知识库先通过 Human Work Item 和 External Reference 闭环，不要求自动同步 Adapter。

### 4.3 V1 明确不做

- Shared Team Mode 服务和实时多人协作；
- Teams、飞书、邮件等外部协作同步；
- 通用聊天、自由评论和社交动态；
- 自动监听告警、Issue 或生产信号创建 Change；
- 通用 Workflow/Policy 可视化设计器；
- Skill/Tool/Adapter 市场与自动安装；
- CodeGraph、向量数据库和企业知识图谱；
- 长期生产日志、Trace、SLO、业务指标和用户行为平台；
- 多集群、多区域和大规模渐进式发布编排；
- 在线 Solo/Team 双向同步或分叉历史自动合并；
- 组织级账号、计费、配额和多租户后台；
- LLM 自评直接通过高风险 Gate。

## 5. V1 内置 Profile 验证范围

| Profile | V1 要求 | 必验路径 |
|---|---|---|
| Feature | 完整支持并作为北极星场景 | Contract→Plan→Execute→Evaluate→Test→Production→Close |
| Bugfix | 完整支持核心路径 | 独立评价失败、Repair Work Item、新 Artifact 与回归证据 |
| Incident | 支持压缩应急路径 | 最小应急授权、一次性权限、Recovery、核对与强制复盘 |
| Security Fix | 可配置 Profile 定义 | 复用基础状态机；职责分离和 Evidence 规则可表达 |
| Migration | 可配置 Profile 定义 | 恢复、数据影响和不可逆规则可表达 |
| Experiment | 可配置 Profile 定义 | 允许在授权验证终点不进生产而关闭 |
| Tech Debt | 可配置 Profile 定义 | 行为不变 Claim 与基础流程可表达 |
| Ops Change | 可配置 Profile 定义 | 外部副作用、Environment 和 Recovery 可表达 |

“可配置 Profile 定义”表示 Protocol 与 Policy 可以表达，不表示 V1 必须分别提供完整专用 UI 和独立端到端认证套件。

## 6. 实施里程碑

里程碑按可演示、可验收的纵向能力定义，不按代码模块完成度定义。当前不绑定日历日期；在技术选型和团队容量确认后再估算周期。

### M0：协议与可恢复 Kernel 骨架

交付：

- V1 对象 Schema、ID、Reference、Command/Event Envelope；
- SQLite Store Port 基础实现；
- Aggregate Revision、Event Ledger、Outbox 和幂等处理；
- Change 基础状态机、Transition 与重启恢复；
- 最小 CLI/测试入口。

退出条件：

- 可以创建 Change、执行合法/非法迁移并解释结果；
- 重复 Command 不重复写入；
- 进程在事务提交前后中断均不会产生“有状态无 Event”或重复 Outbox；
- Event/Current State 一致性测试通过。

### M1：意图、计划与人工决策

交付：

- Draft Change 与 Change Room 基础页；
- Contract/Amendment、Risk、Profile；
- Intent Decision；
- Plan/Task DAG/Amendment；
- Knowledge Impact Assessment 与必需 Knowledge Task；
- Technical Decision；
- Actor、Role、Assignment 与本地 Policy；
- Decision Inbox 和结构化反馈。

退出条件：

- 一个需求可以形成 Contract v1 并获批进入 IntentReady；
- Plan v1 获批后进入 Planned；
- request changes、reject、过期 Decision 和 Revision 冲突均有确定行为；
- 知识影响可以明确判定为 Create/Update/Deprecate/Verify/No Impact，并进入 Task DAG；
- Agent 不能直接批准或修改 Change State。

### M2：执行、上下文与不可变产物

交付：

- Work Item、Task Ready 规则、Lease 与 Resource Lock；
- Claude Code/OpenCode Runtime Adapter（V1 先实现一个）；
- Change Worktree；
- Context Pack Manifest；
- Capability Resolver 与 Binding；
- Planner/Executor Run；
- Source Snapshot、Artifact 和 Run Record。

退出条件：

- Kernel 可以自动为 Ready Task 创建 Work Item；
- Agent Runtime 只能在授权 Worktree 和能力范围内执行；
- 同一 Work Item 重试产生新 Run；授权边界改变产生新 Work Item；
- Artifact 可以追溯到 Source Snapshot、Run、Context 与 Capability 版本。

### M3：Claim–Evidence 与独立评价

交付：

- Claim、Evidence、Requirement Set 与 Gate Evaluation；
- 确定性测试结果提升；
- 独立 Evaluator Run；
- Delivery Evidence Package；
- Valid/Stale/Superseded 影响传播；
- Repair Work Item 循环。

退出条件：

- Artifact 存在或 Run 成功不能直接通过 Gate；
- Refutes Evidence 阻止 ALLOW；
- 评价失败能返回 Executing 并形成新 Artifact；
- Contract/Artifact 改变后只使受影响 Evidence 失效；
- Evaluator 不继承 Executor 完整对话且不能直接修复代码。

### M4：测试、生产与恢复闭环

交付：

- Environment、Release、Deployment；
- 一个真实 DevOps/Environment Adapter；
- 测试部署与 Test Evidence；
- Production Release Decision；
- 同 Digest 生产晋升与即时验证；
- Recovery、Reconciliation 和外部结果未知处理。

退出条件：

- 测试失败触发 Repair 而不是原地热修；
- 生产部署不能使用不同于测试的 Digest；
- Release Approval 只授权一次具体发布；
- 未知外部结果不会触发盲重试；
- 生产验证失败可以执行预授权恢复或进入 AwaitingDecision。

### M5：产品闭环、可移植性与发布加固

交付：

- 完整 Project Workbench 与 Change Room V1 页面；
- Attention Queue、双层时间线和 Run Detail；
- Close、Archive、Cancel、Supersede 与 Learning Candidate；
- Mandatory Knowledge Task、知识更新 Evidence 与 Closure Gate；
- Portable Export/Import；
- 故障注入、恢复、审计与安全检查；
- V1 文档、示例项目与验收脚本。

退出条件：

- 北极星主场景和全部异常场景自动化/半自动化通过；
- Kernel 重启、Outbox 重投与外部核对不会重复副作用；
- Export/Import 保留 ID、版本、Digest 与 Event，并拒绝分叉历史；
- Workbench 可以解释每次状态迁移、失败和待决事项；
- Change Room 可以解释受影响知识、责任人、完成时点、External Reference 与陈旧状态；
- V1 未实现能力不会在 UI、文档或报告中被声称具备。

## 7. 里程碑依赖与纵向演示

```text
M0 Kernel 事实与恢复
→ M1 意图/计划/决策
→ M2 执行/上下文/产物
→ M3 证明/独立评价
→ M4 环境交付/恢复
→ M5 产品闭环/可移植性/发布
```

每个里程碑都应保留可运行演示：

- M0：命令和状态机演示；
- M1：从 Draft 到 Planned；
- M2：从 Planned 到 Artifact Candidate；
- M3：评价失败并修复后通过；
- M4：同 Artifact 测试、生产与恢复；
- M5：完整 Change Room 闭环、重启恢复与 Export/Import。

## 8. V1 端到端验收表

| 编号 | 验收动作 | 必须产生的权威事实 | 通过标准 |
|---|---|---|---|
| A01 | 明确创建 Change | Change、Owner Assignment、Event | 普通对话不自动创建；ID 稳定 |
| A02 | 批准 Contract | Contract Version、Decision、Gate Evaluation、Transition | 版本和 acting role 精确绑定 |
| A03 | 批准 Plan | Plan Version、Task DAG、Decision、Transition | 普通 Task 不逐项人工审批 |
| A04 | 调度执行 | Work Item、Run、Context/Capability Manifest | 权限和版本可追溯 |
| A05 | 构建 Artifact | Source Snapshot、Artifact、Digest、Build Evidence | 内容不可变且来源明确 |
| A06 | 独立评价 | Claims、Evidence、Evaluator Run、Gate Evaluation | 自检不能替代独立评价 |
| A07 | 修复失败 | Failure、Repair Work Item、新 Run/Artifact | 旧失败与旧 Artifact 保留 |
| A08 | 测试部署 | Test Release、Deployment、Test Evidence | 实际 Digest 与目标一致 |
| A09 | 生产批准 | Release、Decision Request、Decision | 授权绑定环境、范围、窗口和恢复策略 |
| A10 | 生产部署 | Deployment、外部引用、即时 Evidence | 使用测试通过的同 Digest |
| A11 | 未知结果核对 | Blocker、Reconciliation、Evidence | 无盲重试和重复副作用 |
| A12 | 恢复 | Recovery Work Item/Deployment、Evidence、Event | 回到已知安全状态且历史完整 |
| A13 | 关闭 | Transition、Closure Event、Learning Candidate | 残余风险和后续事项可追踪 |
| A14 | 重启恢复 | Lease/Outbox 核对和新事件 | 无重复执行或丢失动作 |
| A15 | Export/Import | Manifest、Import Report、重建状态 | ID、版本、Digest、Event 保持一致 |
| A16 | 知识闭环 | Knowledge Impact、Knowledge Task、External Reference、Evidence | 受影响知识已更新/废弃/确认无影响；必需义务未完成时不能关闭 |

## 9. 非功能发布门槛

### 9.1 正确性

- 所有状态迁移经过 Kernel；
- 所有正式写入经过 Command；
- Event 与 Current State 可交叉解释；
- 关键对象引用精确版本或 Digest；
- 不存在通过 UI、Adapter 或 Agent 直接改状态的通道。

### 9.2 可恢复性

- 支持进程重启、Lease 过期、Outbox 重投和外部状态核对；
- 对未知结果停止盲重试；
- 每个副作用操作具备幂等键或明确不可幂等处理；
- 恢复动作保留完整历史。

### 9.3 安全与权限

- Work Item 使用最小权限；
- 凭据不进入 Prompt、Context、Event、Artifact 元数据或 Export；
- 生产权限一次性、范围化和限时；
- Agent 不能承担 Human-only 决策角色；
- break-glass 有范围、时限、Evidence 和复盘。

### 9.4 可审计性

- 可以从任一 Transition 追溯到 Gate、Decision、Evidence、版本和 Actor；
- 可以从 Artifact 追溯到 Source、Run、Context 和 Capability；
- 可以从 Deployment 追溯到 Release、Artifact、授权和外部事实；
- 历史不可被后续重试、修订或恢复覆盖。

### 9.5 可移植性

- Store 实现不进入领域 Schema；
- Portable Export 不依赖 SQLite 文件格式；
- Import 可以重建 Read Model；
- External Reference 不可用时明确标记；
- 自动测试验证 Solo 数据可进入 Team-compatible Store 实现。

## 10. 实施策略

### 10.1 先做纵向薄切片

每个里程碑优先实现一条端到端可运行路径，再扩充对象字段和边缘能力。禁止先建设庞大通用平台，最后才尝试把 Change 跑通。

### 10.2 先契约测试，再替换实现

以下边界优先建立实现无关的契约测试：

- Store Port；
- Runtime Adapter；
- Workspace/SCM Adapter；
- DevOps/Environment Adapter；
- Capability Provider；
- Export/Import；
- Gate/Policy Evaluation。

SQLite、PostgreSQL、Claude Code、OpenCode、未来 cimicode 或具体 DevOps 实现都必须通过各自边界的相同语义测试。

### 10.3 不以 Mock 闭环冒充产品闭环

单元测试可以 Mock 外部能力，但 V1 发布验收必须至少使用：

- 一个真实 Git 仓库；
- 一个真实 Claude Code 或 OpenCode Agent Run；
- 一个真实构建结果；
- 一个真实测试环境部署；
- 一个受控真实生产环境部署；
- 一次真实外部状态核对或故障注入。

## 11. Build / Adopt / Adapt 映射前置条件

外部项目映射必须以本范围为需求基线。对每个候选能力回答：

1. 它满足哪个 Capability Definition；
2. 它是否试图成为核心状态或事实权威；
3. 它的身份、版本、权限、幂等、健康和核对能力如何声明；
4. 它输出的哪些内容提升为 Artifact、Evidence、Run、Deployment 或 Event；
5. 替换它是否需要改变 Cimi Change Protocol；
6. 应选择 Build（自建）、Adopt（直接采用）还是 Adapt（通过适配层采用）。

映射顺序建议：

1. Claude Code/OpenCode Runtime 与本地执行，cimicode 作为后续企业内部适配目标；
2. Git/Workspace；
3. DevOps/Environment；
4. OpenSpec 等 Contract/Spec 能力；
5. Matt Pocock Skills（包括 grill-me、domain-modeling 等）与其他研发 Skills；
6. Superpowers；
7. CodeGraph、Multica 等 Code/Knowledge 分析；
8. 外部协作与 Team Mode 能力。

## 12. V1 Definition of Done

CimiLoop V1 只有在以下条件全部满足时才算完成：

- 北极星 Feature 场景真实闭环；
- 八类异常验收场景通过；
- Feature、Bugfix、Incident 三类关键 Profile 路径通过；
- 三项基础 Human Decision 不可绕过；
- Executor/Evaluator 分离有效；
- 测试与生产同 Artifact Digest；
- 重启、重试、未知结果和 Recovery 不破坏历史或重复副作用；
- Workbench 能解释当前状态、停留原因、责任角色、证据和下一动作；
- 每个 Change 完成知识影响评估，Mandatory Knowledge Task 通过 Evidence 闭环，已知陈旧知识不能被静默带入关闭状态；
- Portable Export/Import 保留核心身份与历史；
- 所有 V1 非目标在产品和文档中明确，不被宣传为已实现。

## 13. 阶段结论

V1 选择“窄范围、完整闭环”：先把一个真实 Change 从创建可靠地送到生产并关闭，同时证明失败、恢复、重启和迁移不会破坏权威历史；不以增加更多 Profile、Agent、平台集成或团队功能扩大表面范围。

上述范围、验收路径、M0–M5 里程碑与 Definition of Done 是 2026-09-19 确认的旧 V1 基线。按新流程重对齐后才能重新作为直接实施依据；原阶段结论不覆盖本文开头的适用性提示。任何新增能力都必须说明其服务的验收目标和对范围、风险与里程碑的影响。
