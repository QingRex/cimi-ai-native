# S1 收束后端 B0 报告

日期：2026-10-28。最终依据为收束决定修订后的 §6。Schema 242、项目库格式 10、Host 1 不变。

## 最终设计

实施由当前 Human 借助本地模型完成。WorkItem.executor_ref、Kernel caller、命令 actor_id、原始结果 producer_actor_id 都绑定该 Human；RunRecord.run_kind 为 human，使用现有 manual_run / manual_evidence 格式。模型只是工具，不登记 Agent 或第二个 Human，不创建或修改 ProviderBinding。旧正式 Agent 准入代码保留。

单人规则在 Kernel 命令执行时从 actor 列表推导：只统计 actor.project_id 等于当前项目且 actor_type 为 human 的项，数量恰好为 1 才是 solo。没有开关、持久化字段或迁移。

- execution.ts：仅当 WorkItem 执行者也是 Human 且项目处于 solo 时，跳过实施与独立验证 WorkItem 的同身份冲突。反向先验证后实施的身份冲突也按同一条件处理。
- verification.ts 的 independentProblem：保留 independence_required、禁止 edit_files、Human 执行者三项要求；仅在 solo 时不检查该执行者的实施 WorkItem 历史。准备评价、EvaluateTask、SatisfyTask 和集成评价均调用此函数，按各次命令的当前 actor 列表判断。
- 两个及以上 Human 时完全沿用原身份冲突规则；高风险专业复核、反证、固定上下文和源码一致性等规则不变。
- 计划的 independent 模式、评价 purpose 和只读 context 沿用现有协议字段；真实 producer 仍是当前 Human。solo 验证原始证据的 method 明确记录“单人模式 · 非独立验证”；前端可从治理 actor 列表按同一规则标注，无新增响应字段。

工作台不显式传 planningClarification 时，复用 legacyManualPlanning:true，不安装阻塞人工计划的 Matt 端口。因此 SubmitPlanProposal / ConfirmPlan / InitializePlanTasks 使用现有人工兼容路径；显式传入旧端口仍保留原行为。

LOCAL_COMMAND_TYPES 已开放 AssignResponsibility、TransferChangeResponsibility、UpdateProjectSettings，仍由原 Kernel 校验 project_owner、目标、版本与幂等。StartChange 前先通过现有命令设置项目设置及所需责任角色。

## 现有命令链与源码

1. InitializePlanTasks 后，启动 helper 以 Human technical_owner 创建 WorkItem、捕获 SourceSnapshot；以同一 Human executor 执行 PrepareRunContext → ReserveRun → RecordRunObservation（running）。每 Task 在固定源码 commit 上创建独立 worktree，模型通过受限工具修改。
2. 固定检查结束后，在 Task 分支提交实际修改，保存 base_commit/head_commit、patch、文件统计与检查结果。以 executor 的 RecordRunObservation 记录确定终态，Kernel 清除在途标记、将 WorkItem 恢复 Ready。观察记录相对运行前源码可为 stale；后续任务评价明确使用结果 head_commit 的新 SourceSnapshot，不把运行前快照当作最终源码。
3. 评价 helper 在最终 commit 捕获或复用 SourceSnapshot → PrepareTaskEvaluation 取得 Kernel 的精确需求项 → RecordEvidence → 再次 PrepareTaskEvaluation 固定含新证据的摘要 → EvaluateTask。两次准备避免宿主复制 Kernel 的需求与摘要算法。所有评价项都来自 Human 明确输入，不从模型建议或检查成功自动生成 supports。
4. SatisfyTask 由 Human technical_owner 执行，重新核对评价适用性并关闭 WorkItem。存在任务依赖时，先满足实施任务，再为依赖它的验证任务建单/评价；仅 EvaluateTask=ALLOW 还不会解锁依赖。
5. 验证 helper 可以直接引用实施 Run 的 run_id，创建当前 Human 的只读验证 WorkItem，不要求再启动模型或创建验证 worktree。实施与验证评价复用同一最终 SourceSnapshot；验证的 safe_integration 等非 acceptance 需求由 assessment 明确覆盖。
6. 两个任务均满足后，交付 helper 执行 EvaluateIntegration；仅 ALLOW 时调用 MarkReadyForIntegration，最终状态 ReadyForDelivery。端口核对运行结果所在 worktree 的最终 commit 与 clean 状态，保留用户主工作区。

最小普通 Change 为一个实施任务及随后对同一最终源码的验证任务。后续任务运行默认基于本 Change 最新成功结果。多个实施任务继续改变源码会使旧满足结论不适用，本次不扩展重开任务/合并/重基流程。

## HTTP 形状（保持契约）

所有写请求沿用 Cookie / Origin / CSRF，所有 URL 禁止 query string。每个 helper 的 command_id 为 UUID v7；服务端保存子命令完整输入与响应，同 ID 重放原结果，不重复启动或生成 Kernel 效果；同 ID 不允许更改 action/input。

### 启动运行

`POST /api/tasks/:taskId/agent-runs`

请求：`{"command_id":"<uuid v7>","instruction":"可选补充说明"}`（instruction 可省略）。

响应：`{"ok":true,"run_id":"…","task_id":"…","status":"Running"}`。

创建 WorkItem、捕获源码为 Human technical_owner；准备、预约、观察为绑定的 Human executor。验证任务只读。命名 agent-runs 保持 HTTP 契约，Kernel 记录为 Human-kind。

### 记录任务评价

`POST /api/tasks/:taskId/evaluations`

请求：

```json
{"command_id":"<uuid v7>","run_id":"…","assessment":{"result":"supports","observation":"对目标、输出、约束、证据及安全集成的人工观察"},"acceptance":[{"key":"<约定 acceptance key>","result":"supports","observation":"本项观察"}]}
```

result 均为 supports / refutes / inconclusive。assessment 明确评价所有非 acceptance 需求；acceptance 必须覆盖该 Task 全部 acceptance key，并对应其子证据项。精确描述及需求 key 从 Kernel 准备结果取得。

响应：`{"ok":true,"task_id":"…","source_snapshot_id":"…","evaluation_id":"…","outcome":"ALLOW","reasons":[]}`。outcome 也可能为 NEED_MORE_EVIDENCE / REQUIRE_HUMAN / DENY。

角色为当前 Human executor；捕获源码及尚无 WorkItem 时建单为 technical_owner。run_id 必须为当前 Change 的成功 lite Run；独立验证可以引用实施 Run，solo 允许同一个 Human 完成。

### 标记任务满足

`POST /api/tasks/:taskId/satisfy`

请求：`{"command_id":"<uuid v7>","evaluation_id":"…"}`。

响应：`{"ok":true,"task_id":"…","status":"Satisfied"}`。角色 Human technical_owner。

### 评价集成并交付

`POST /api/changes/:changeId/ready-for-delivery`

请求：`{"command_id":"<uuid v7>","run_id":"…","reason":"交付理由","deferred_checks":[]}`。deferred_checks 可省略（默认 []）；非空项沿用现有 DeferredVerification：`{"acceptance_key":"…","reason":"…","responsible_actor_id":"…","environment":"test","next_check_at":"<UTC>","method":"…","required_before":"before_release"}`，environment / required_before 枚举沿用 Kernel。

响应：`{"ok":true,"change_id":"…","evaluation_id":"…","outcome":"ALLOW","reasons":[],"status":"ReadyForDelivery"}`。未 ALLOW 时返回实际 outcome/reasons 和 `"status":"Executing"`，不调用标记命令。角色 Human technical_owner。

## Lite 执行器及其余接口

- 全局 fetch 调用 OpenAI-compatible chat completions；list_dir / read_file / search_text（git grep）/ write_file / run_check 工具，文件路径限制在 worktree，写入另受 WorkItem 资源与只读边界限制。
- 每 Task 一个 cimiloop/task-<short id> 分支和数据目录内 worktrees/<taskId>。运行事件和 result.json 位于 .git/cimiloop/runs/<runId>/，无数据库表变更。
- ~/.config/cimiloop/provider.json 提供 base_url、model、max_turns、max_tokens，默认 30 / 200000。macOS Keychain 优先，环境变量后备；密钥仅用于 Authorization，运行输出脱敏，子进程环境移除该变量。
- 旧固定检查为正式 Windows WorkspaceCheckTemplate，lite 使用项目数据目录 checks.json 的 `[{"name":"check","command":"pnpm check"}]`，缺省该单项。只允许配置名称，模型结束后自动执行全部固定检查。worktree 的依赖由项目环境或明确配置的检查命令提供，不自动安装依赖。
- 轮次和 token 配额限制分派；缺 usage 时以 UTF-8 字节保守计数。AbortController 取消 fetch，并终止固定检查进程组。停止先执行原 CancelRun，确定终态用 ReconcileRun 结清；重启遗留 Running 记录为 Unknown，不自动恢复/重试或认定成功。
- SSE 按 seq 写 id、支持 Last-Event-ID、回放后在 done 关闭。路由拒绝 GET 请求体并禁用响应 socket 超时；10 秒 requestTimeout 只限制请求接收，不截断已完整接收的 SSE GET 响应。
- result 按契约返回 commit、patch、文件统计、检查和 usage；patch 超过 1 MiB 时截断并带 patch_truncated。
- AI clarify / review 只返回建议，不写 Kernel；未配置模型时返回 409 MODEL_NOT_CONFIGURED。context.runtime 维持原契约，未配置时 provider=null。
- 所有 helper 与契约 §2.1–2.4、§3.1 的形状无变更，旧正式 Agent 准入链保持。
