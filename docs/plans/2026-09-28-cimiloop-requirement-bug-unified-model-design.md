## 已确认的模型

1. 项目内共用一个需求池，以需求、缺陷两种业务类型区分记录。
2. 需求池是全部需求与缺陷的统一台账，不是仅显示待规划或未挂版本记录的容器。
3. 版本指规划归属的目标版本，可以为空；实施前也不强制指定。
4. 录入允许只有一句话，先进入澄清，不等于批准正式实现。
5. 澄清可以细化原记录、拆成多个独立记录，或判断不进入交付。
6. 对需求和缺陷这条路径而言，业务记录就是内部 Change，从录入到交付只有一个业务身份，不另建一套一一对应的对象与生命周期。
7. 不采用子需求层级；拆分后的记录是平级独立 Change，只保留溯源关系。
8. 原记录标记已拆分，保留原文及澄清记录，不能计为已交付。
9. 确认要做是交付授权过程的关口，不再是创建 Change 的时机；正式实现仍需满足有效授权及流程检查。
10. 通过必要验收且达到约定交付终点才算已完成；通常以实际上线为终点，验收通过但未发布仍待发布。
11. 集成测试发现问题后先评估并尝试修复；若最终无法在约定上线窗口前修复，则从本次交付范围剔除并延期到后续版本。
12. 上线前从共享 feature 集成分支切出 release 分支，固定本次发布候选范围，不直接以持续变化的 feature 分支头作为生产发布来源。
13. 发布候选验证期间，现有测试环境切到 release 并暂停 feature 对该环境的覆盖；这不等于停止 feature 的开发或合入。

## 主流程与对象边界

录入 → 澄清 → 批准明确的交付范围 → 计划与任务 → 受控实施 → 验证与交付。

需求池是视图，不维护第二套事实。目标版本组织同一批记录，不代替实施授权；业务类型、处理进度、目标版本是不同维度。

一个业务身份不要求所有内容放进同一数据对象。Contract、Plan、Task、Work Item、Run、Evidence、Decision、Release 等仍保持各自职责和历史边界。

```text
R100：提升订单处理效率
    ──拆分来源──→ R101：支持订单批量审核
    ──拆分来源──→ R102：异常订单自动提醒

R100：已拆分，保留来源及澄清记录。
R101 / R102：平级独立需求，各自澄清、授权、实施和验收。
```

拆分关系不是父子控制；关闭或归档原记录不能级联关闭新记录。各记录可以有不同负责人、不同目标版本，或没有目标版本。

可独立验收业务结果才适合拆成需求。后端、前端、测试通常是任务；权限和边界约束可能只是验收标准。AI 辅助提问、提出验收和拆分建议，由人确认拆分结果。

## 对此前候选方案的修正

不再采用先建需求、确认要做后再创建独立 Change 的方案。现有 Draft 已承担澄清与授权前准备；两份业务对象会增加身份、范围和状态同步负担，当前没有要求两套独立生命周期。

不采用每个任务一个 Change，也不采用父需求控制拆分记录的生命周期。

## 保留的 AI Native 约束

创建记录、指定版本、提出拆分建议都不是正式实现授权。Task 是持久任务，Work Item 是执行授权，Run 是一次尝试；Run 成功不能代表事项已交付。

授权依据明确的范围、约束和验收约定；实施、独立验证、证据、决策及发布保留历史和精确依据。目标版本可空，实际发布仍须有受控发布记录与制品依据。

## 共享集成与发布规则补充

### 已确认的业务场景与规则

多条需求 / 缺陷在各自分支开发、自测后，合入共享 feature 集成分支，再部署测试环境供产品或测试验证。测试环境随着新的合入或修复持续更新，发布不必等待所有需求同时开发完成。

本次发布中的某条记录未通过验证时，先看能否修复；如果最终无法在约定上线前修复，则剔除本次范围、安排到后续版本。延期不改变业务身份，也不代表取消或已完成；当前版本的原规划与实际交付差异应保留。

已确认下一目标版本时调整规划归属；若后续版本尚未明确，目标版本仍可为空，不为延期创建强制版本前置条件。

### 已确认的发布分支策略及约束

共享 feature 用于持续集成；上线前从其确定快照切出 release 分支，固定本次发布候选范围。冻结范围不意味着禁止修复或剔除；这些操作改变了发布内容，必须形成新的候选制品并重新验证。

```text
各需求开发分支 → feature → 持续集成构建 → 测试环境验证
                   │
                   └─ 切出 release → 本次范围的修复 / 必要剔除
                                      → 新构建及最终验证
                                      → 同一获批制品晋升生产

feature 后续的新合入不自动进入已切出的 release。
```

生产发布绑定 release 的精确提交和制品，不仅绑定分支名。release 与先前 feature 测试快照的内容不同，则先前测试不能直接代表最终发布候选已通过；需要对实际候选完成必要验证。

feature 可以继续接收后续研发成果，但发布候选验证期间不得覆盖已切到 release 的测试环境。修复回流、延期代码及生产基线同步策略尚待确认，不能机械把 release 中的剔除带回后续研发范围。

### 已确认的测试环境占用策略

同一测试环境分阶段使用：持续集成阶段允许 feature 构建部署；进入发布验证阶段后切换到 release，本次验证期间只允许当前发布范围的 release 制品更新该环境。

暂停的是 feature 对测试环境的部署，不是停止开发、合入或构建。release 的修复、剔除及重建仍走受控部署，每次验证绑定实际环境与制品，不能只依据分支名称或页面显示的版本判断。

后续实现需保护环境占用边界：切换时核对已经在途的部署，切换后阻止旧 feature 任务或排队流水线覆盖 release。仅关闭新的触发入口不足以避免旧任务晚到覆盖；具体中止、等待或核对方式需按现有 DevOps 能力设计。

release 验证通过后，生产晋升同一获批制品。测试环境何时解除发布占用、恢复 feature 部署，以及发布取消或失败后的恢复规则，尚待明确，不能在每次部署结束时自动解除。

### 对现有发布模型的诊断与修订建议

本轮同步前，工程交付模型允许同一 Artifact 被多个 Change 引用，但将 Release 限定在单个 Change 范围内，集成章节主要处理同一 Change 内的多 Task。这一缺口已在专项文档中修订为项目级共享发布与跨需求集成。

专项文档区分需求生命周期与项目级发布流程：需求跟踪自身范围、验收和交付结论；发布版本固定集成快照、制品及实际纳入范围，关联多个需求。目标版本是可选规划归属，发布版本是实际交付内容。高层关系与逻辑流程已同步，物理对象结构、完整枚举与迁移仍待确认，本次不修改协议代码。

### 剔除后的工程约束

1. 剔除前识别代码、接口、配置和数据依赖；其他需求依赖被剔除内容时，不能仅从清单删除一行就宣称可单独发布。
2. 从 release 的实际发布来源中移除受影响实现，例如通过受控 revert 或重新组织发布来源；不删除共享 Git 历史或研发成果。具体剔除操作及依赖处理待确认。
3. 发布范围和构建输入改变后生成新的集成快照、制品和实际纳入清单，不改写旧构建、测试或批准记录。
4. 对新制品开展必要的受影响回归与整体集成检查；既有证据须经明确适用性评估，不能自动把旧制品通过结论转移到新制品。
5. 针对新的范围、制品和环境重新核验发布授权。生产部署晋升实际验证通过且获批的制品，而不是临时读取变化中的分支头。
6. 若无法在窗口内安全剔除并完成验证，也不能为了按时上线绕过发布关卡。

例如 B1 包含 A、B、C、D，D 延期后形成 B2，仅纳入 A、B、C。B1 的失败与修复尝试保持历史；B2 完成必要验证并获批后才晋升生产，D 在原记录下继续修复与后续交付。

## 后续验证场景

- 一句话可建立待澄清需求，不产生正式实现授权。
- 两种类型共用台账且可筛选；无目标版本的记录可合法进入受控实施。
- 指定版本不自动改变授权或实施状态。
- 细化保持身份；拆分生成独立身份并保留来源。
- 已拆分不计为已交付；关闭来源不级联关闭新记录。
- Agent 运行结束不自动把需求或缺陷标记为完成。
- 验收通过但尚未达到约定交付终点的记录不能计为已完成。
- 问题先修复；赶不上约定窗口时延期，业务身份及原版本规划历史保留。
- 从清单剔除但代码仍在制品中的情况不能被视为成功剔除。
- 剔除引发新制品时，必须完成必要验证并重新核验授权，不能沿用旧通过结论自动发布。
- 切出 release 后，feature 新合入不能自动改变本次发布候选；release 修复或剔除后的最终制品须有对应验证记录。
- 测试环境切到 release 后，新发起、排队及在途的 feature 部署不能覆盖发布验证环境；具体处置需遵守环境切换规则。
- 暂停 feature 的环境部署不等于停止 feature 的开发和合入；生产仍晋升实际验证通过的同一制品。

## 一句话表述

大家录入和跟踪的仍然是需求与缺陷；一句话诉求先澄清，必要时拆成独立记录，再在同一身份下完成受控实施、验证和交付。Change 是内部协议名称，不是用户需要额外维护的第二份对象。
