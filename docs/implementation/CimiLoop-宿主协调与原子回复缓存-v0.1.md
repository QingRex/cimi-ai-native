# CimiLoop 宿主协调与原子回复缓存 v0.1

2026-10-05，V1-09续批，决策D-204。实现宿主协调器演练，将持久预留 / 发送、D-203固定连接HTTPS、限定公开回复缓存及关闭接起来。新增显式积分存储格式2，在同一SQLite事务提交回执与回复，覆盖缓存容量竞争、实际宿主退出和取消边界。生产宿主工厂仍在任何副作用前拒绝真实计费；本批只用公开测试Key及本地TLS，不读取实际Key、发送实际模型请求、启用正式Task / Agent或升级用户库。

## 1. 显式存储格式与缓存边界

`GatewayCreditLedger`原默认格式1继续保留。只有受信宿主代码显式传入第四参数`response_cache`，才创建格式2；application_id仍为`0x43494d43`。两种格式互相拒绝打开，不自动转换，不向既有格式1增加表。旧TEST账本和领域数据库格式8保持。

格式2新增STRICT表`credit_cache_policy`及`credit_responses`。缓存策略固定scope=`credit_budget_rehearsal`、每项最大270336字节、总内容上限和最多4096项；总内容上限最多16MiB，不可通过重新打开提高或换策略。策略及回复从调用者数据复制为固定顺序，不依赖属性顺序或后续修改。

每项完成只缓存D-203接受的公开文本、结束原因、观测用量、请求ID、原发送字节摘要、原始响应摘要及始终false的证明字段。缓存不收录请求消息、原始JSON、Header、思考文本或Key。公开文本本身可能包含用户业务信息；未来实际缓存仍需要受保护目录和访问策略，本演练不批准任何真实账户路径。

`reserve`在原预算事务内预留一个缓存位置和最坏270336字节，计入其他reserved / dispatching的预留及已完成缓存的实际UTF-8字节。容量不足时拒绝新请求，不取得新的积分预留、DNS或HTTP；跨宿主也不能超额。没有自动淘汰已完成回复。Unknown释放尚未写入的缓存空间，但保留全部积分预留与原请求身份，不能再次完成或发送。

这是逻辑内容与项数边界，SQLite页面、WAL及文件系统总量不在该上限中，不能代替文件系统硬配额。

## 2. 回执与回复同一事务

格式2必须走`completeCached`，拒绝只提交回执。它先验证限定回复契约，绑定原请求ID、发送字节摘要、原响应摘要和用量，再在一次BEGIN IMMEDIATE事务内插入回复、更新completed回执，并核验整份账本。宿主在写入前及提交前检查取消 / 时限；检查失败会一起回滚缓存和完成状态。

根据[SQLite事务规则](https://www.sqlite.org/lang_transaction.html)，缓存与回执放在同一事务内，避免跨文件提交的中间状态；继续采用WAL和[FULL同步](https://www.sqlite.org/pragma.html#pragma_synchronous)。本批验证语句失败回滚和进程退出，没有实施断电测试，也不声称验证了磁盘控制器的持久化行为。

重开时同时验证缓存策略、表结构、外键、缓存内容摘要及回复与回执的语义绑定。缺失缓存、变化的用量、额外思考字段或虚假准入字段均拒绝，不补写、修复或重发。内容摘要用于一致性检查，不能代替受保护目录或认证；拥有写权限的人可能重算摘要。

同键completed返回原回执及限定回复，没有新发送权、DNS或网络。费率观察到期后历史回复仍可读；新预留和dispatch继续拒绝过期费率。相同完成可幂等读取，改变已完成的回复或用量会冲突。

## 3. 宿主顺序、取消与关闭

`GatewayHostRehearsal.execute`同步冻结消息，预留积分与缓存空间，持久提交dispatching，然后才进入DNS、TLS和HTTPS。各阶段共享同一单调时限，HTTP阶段继承剩余时间；只有完整受限回复通过、原Socket关闭得到观测、取消 / 时限检查通过后，才提交原子完成。

显式取消、时限、网络或契约失败保留Unknown及全部积分预留，无缓存、无重试。观测用量超界会在同一持久失败处理内封锁账户；即使取消同时到达，也保留超界事实。缓存或账本故障不报告成功，不能把底层错误正文、Key或未经核验的回复带给调用者。

取消与完成有明确先后：提交前的取消回滚完成并转Unknown；完成已经提交而结果尚未交付时，取消可以让调用者收到错误，但不会把原completed回执改成Unknown或删除回复。调用者随后按同键读取原完成结果，不再发送。SQLite同步提交期间不能由JavaScript抢占；提交后检查若发现超时也按上述方式保留真实完成，不宣称已退款或重新发送。

`close`立即拒绝新调用、取消全部在途操作，等待它们的finally后才关闭所持Ledger实例；并发close共享同一Promise。TLS Socket按原对象关闭，并有界等待close观测；无法确认时该调用报告关闭未证明。宿主控制点也响应取消，不因未完成的受信故障注入函数无限等待。此处没有创建AppContainer或Job，不能据此声称完成了正式Runtime隔离资源恢复。

## 4. 原宿主退出后的两种结果

实际Windows子宿主在HTTP回复核验后、缓存事务前以73退出：账本仍dispatching，没有回复。原OS身份核对为absent后，D-202恢复将其转Unknown；积分不减少，同键拒绝发送。

另一实际子宿主在原子完成提交后、结果返回前以73退出：重开可读取原completed回执和缓存。无需重新发送；完成事实不依赖原宿主仍活跃。只验证这些退出位置，未声称覆盖真实模型的账单、AppContainer、IPC网关及整个受控运行的崩溃恢复。

另外两个独立子宿主同时争抢一个缓存位置，只有一个进入HTTP并完成；另一宿主在预留时得到`credit_response_cache_exhausted`。本地服务只收到一次请求。原生只读身份辅助进程不计作业务宿主或模型Runtime。
