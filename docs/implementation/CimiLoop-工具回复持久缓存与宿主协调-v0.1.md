# CimiLoop 工具回复持久缓存与宿主协调 v0.1

2026-10-05，V1-09续批，决策D-206。显式积分格式3承载D-205工具 / 有界SSE回复，新增工具宿主协调演练，将发送前持久预留、固定连接HTTPS、原子回执 / 缓存、取消及原宿主恢复接通。本批只使用公开测试Key与本地TLS；生产工厂仍先拒绝真实计费，没有实际Key读取、模型请求、OpenCode工具执行、IPC扩展或正式Task / Agent启用。

## 1. 格式3与最小校验契约

`GatewayCreditLedger`默认仍为格式1；原`response_cache`明确选择文本格式2。受信宿主传入新的`conversation_cache`才创建格式3，三者互相拒绝打开，不隐式转换。application_id继续`0x43494d43`；领域8、旧TEST1及用户数据库保持。

格式3在原STRICT账户、预算、拥有者、请求及缓存表之外增加`credit_conversation_contracts`。每次预留在同一事务写入积分请求和最小工具契约，分别保存摘要；不能先取得发送权再补契约。旧reserve / completeCached拒绝格式3，新reserveConversation / completeConversationCached拒绝格式1 / 2。

最小契约格式为`cimiloop/conversation-cache-contract/1.0.0`，只保留请求ID、实际发送字节摘要、输入 / 输出边界、json / sse响应模式、工具名、参数Schema及历史调用ID。它从原Transport拥有的冻结请求取得，不能从复制的请求或其他实例读取。工具描述及Schema的description元数据不入契约；名为description的业务属性和enum / const业务值仍保留，不能删掉实际校验语义。

契约根及JSON对象键按确定顺序保存，数组保持声明顺序；重新打开会重新核验Schema子集、字段、摘要和绑定。原发送摘要仍覆盖全部消息、工具描述、历史结果、模式及模型参数，修改任何实际发送内容都会冲突。最小契约无法在没有原请求正文时重算发送摘要；其联系由受信Transport和预留事务建立，摘要不是防篡改认证。后续实际账户路径仍需受保护目录。

契约不保存提示词、历史assistant正文、工具结果正文、历史参数或reasoning_content；回复只保留D-205已核验的公开文本 / 工具提议、用量和摘要。工具名、Schema的业务常量、历史调用ID及公开回复 / 参数也可能包含业务信息；最小化不意味着数据公开，本演练没有批准实际业务缓存路径。

## 2. 容量、原子完成与重放

每项最小契约最多65536字节，每项限定回复最多270336字节。格式3总逻辑内容上限最多16MiB、最多4096项；最小可配置容量335872字节，可容纳一项最坏契约和回复。策略在创建时冻结，重开不能增加额度或更换格式。

reserveConversation在BEGIN IMMEDIATE事务内计入全部已保存契约、已完成回复及所有reserved / dispatching请求的最坏回复预留，再为新请求加入已知契约字节和270336字节回复预留。条目数包括全部保留契约，无论请求是否Unknown。容量不足时不取得新的积分预留、不写新契约、不进入DNS / HTTP。跨宿主争抢同一容量仍由同一事务约束。

Unknown释放尚未写入的回复预留，继续保留全部积分和最小契约；契约仍占条目及实际字节，不能通过失败 / 取消淘汰它来忘记原请求身份。已完成回复也不自动淘汰。此上限只约束逻辑内容，SQLite页面、WAL、目录总量及物理硬配额仍待实现。

completeConversationCached按原契约重新核验工具名、参数Schema、历史调用ID和始终false的准入 / 执行字段，并绑定原请求、输入摘要、原响应摘要及回执用量。回复INSERT与completed回执UPDATE在同一SQLite事务；写入前和提交前的取消 / 时限检查失败会整体回滚。用量超过原预留边界仍转Unknown并封锁账户，不写回复、不减少积分预留。

重开时必须每个请求恰好有一项契约、每个completed恰好有一项回复；缺失、摘要损坏、额外字段、未知工具、无效参数、旧调用ID复用或回执用量不一致都拒绝，不修补和重发。即使回复摘要被重算，语义仍需通过原契约及回执核验；有写权限的人若连原契约和回执一并改写，摘要不能提供认证。

相同completed请求返回原回执及深冻结回复，无新发送权、DNS或HTTP。过期费率仍允许读取已有完成，新预留 / dispatch继续拒绝过期费率。重放工具提议不证明工具已执行；后续工具执行必须另有受控操作身份和幂等恢复，不能将模型回复缓存当作工具副作用去重记录。

## 3. 工具宿主的发送与取消顺序

`GatewayConversationHostRehearsal`只接受格式3，原`GatewayHostRehearsal`仍只接受格式2。两者共用一个内部协调实现，防止文本 / 工具路径的取消、提交、关闭规则分叉。策略由固定受信构造器选择，没有CLI、Runtime JSON或调用者approved开关。

准备并冻结请求，先核验公开测试Key不出现在发送正文或解码后的历史参数，再预留积分 / 契约 / 回复容量；持久提交dispatching之后才DNS、TLS和HTTPS。HTTP继续只沿一次验证的原Socket发送，工具 / SSE完整核验并确认Socket关闭后，才提交原子完成。

所有阶段共用一个单调总时限。取消、超时、网络或契约失败保留Unknown及全额积分，无回复、无自动重试；用量超界封锁仍保留。提交前取消不完成，提交后交付前取消可以使本次调用报错，但不能删除真实completed事实；同键随后读取原回复，不再次发送。

close拒绝新工作、取消并等待全部在途finally、确认准确Socket关闭，再关闭Ledger；并发close共享Promise。该宿主只协调本地TLS和SQLite，没有启动AppContainer / Job，不能据此声称完成了正式Runtime资源恢复。

工具结果轮次用新的全局请求ID，把原调用提议和关联结果带回D-205消息契约。验证中的工具结果由公开合成fixture提供，没有实际工具执行器；参数Schema通过也不批准路径、命令或WorkItem能力。所有新回复的tool_execution_authorized、billing_admission_ready及actual_cost_known仍false，formal_execution_enabled也保持false。

## 4. 实际宿主退出与验证

三个实际Windows子宿主分别在回复核验后、回复INSERT后但completed UPDATE前、原子完成提交后以73退出。前两种重开均无completed回执和回复；第二种证明未提交事务中的INSERT整体回滚。按原PID / 创建时间 / image核验OS身份为absent后，待处理请求恢复Unknown，保留契约和全额积分，同键不重发。第三种直接读取原completed回执和工具缓存，无新HTTP。

另外两个独立Windows子宿主争抢最后一个契约 / 缓存位置，只有一个预留并进入HTTP，另一宿主在预留时拒绝。本批新增5个独立子宿主；原D-204文本宿主回归另行运行，身份辅助查询不计业务宿主，也没有通过数值PID杀进程。
