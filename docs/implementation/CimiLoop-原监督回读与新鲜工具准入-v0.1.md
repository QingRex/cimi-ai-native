## 已接入的执行路径

Agent 文件工具与固定 Node 检查宿主在每次新鲜 Kernel 授权评估之前，先以可取消的 setImmediate 让出事件循环，再核对宿主停止信号并执行原评估。固定检查逐个文件和 run_checks 均执行此边界，不能只在整个配方开始时让出一次。共享应用服务的实际 Runtime 组合直接使用这两个宿主，没有第二套业务权限或额外 Run。

原 Kernel 评估、Native 权限核验、二进制物理原件和摘要、原输入 / 源码 / 授权依据的再次核对均保留；SQLite 事务内部没有异步间隙。最终评估之后至效果之间没有新增宏任务让出。原 dispatch、原请求 / 响应账本、唯一 Run 启动、响应丢失不重发、未知结果不升级的语义保持。

让出给待处理时钟管道与停止回调执行机会，不保证所有管道响应已交付。Native clock_continuous 的原 15 秒期限未延长，迟到响应仍拒绝；单次同步评估自身过慢仍可能触发期限。关闭在让出期间到达时，返回原 host_closed 类别。初次评估前关闭不预约工具 / 检查；新增合同中的 Native 准备前中间关闭保留原已登记 claim，记录未 dispatch 停止；已 dispatch 后关闭或撤销保留原 dispatch 和 Unknown，不执行或重发原效果。

## 原反例与证据边界

修复前独立实际 Windows / OpenCode 读改查诊断通过，但记录到同一时钟响应 Native UTC 至宿主处理相差 13,589ms，相邻事件循环间隔 13,594ms。该片段内同步核验包含 39 次 Node 原二进制读取，共 3,620,191,224 字节，以及 12 次原启动账本 Native 权限核验。读取计时不包含摘要计算，不能把全部延迟归因于单一读盘或权限调用。

诊断包装只记录指定程序 / 二进制的时间、字节数和时钟序号；不记录参数、环境、密钥或模型正文。因实际组合使用编译后的另一模块实例，源码 Clock.read 包装没有采集到端到端调用时间；Native UTC 至宿主 data 回调的延迟是交付观测，不能冒充完整时钟调用期限。心跳最大片段也不等于当时一定有等待中的时钟请求。

这确认当前同步链可能延迟原监督回读，尚未证明 D-249 原失败的唯一根因。D-249 原 clock_continuous 中断、此前 Bun / CLR 异常和历史 Unknown 原件继续保留；后续独立新夹具通过不覆盖旧失败，不重开旧 Run，不从当前源码补造旧结果。
