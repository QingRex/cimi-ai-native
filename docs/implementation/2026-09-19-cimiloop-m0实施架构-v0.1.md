## 1. M0 目标

M0 不追求完整业务流程，而是证明 CimiLoop 最基础的可信运行机制成立：

```text
初始化 Project
→ 创建 Draft Change
→ 查询 Change
→ 暂停并恢复 Change
→ 非法操作得到稳定错误与解释
→ 重启进程后恢复权威状态
→ 重复 Command 不重复产生 Event 或 Outbox
```

`Draft → IntentReady` 需要真实 Contract、Risk、Profile、Decision 与 Gate，属于 M1。M0 不用临时标志或假批准绕过这些语义。

## 2. 技术基线

| 项目 | 选择 | 约束 |
|---|---|---|
| 语言 | TypeScript | 开启 strict，不允许以 `any` 绕过 Protocol 边界 |
| 运行平台 | Node.js 24 LTS | 最低使用包含 Release Candidate `node:sqlite` 的 24.15；工程锁定具体 24.x 版本 |
| 模块系统 | ESM | 包使用明确 `exports`，不混用 CommonJS |
| 包管理 | pnpm Workspace | 根 `package.json` 锁定准确 pnpm 版本 |
| 编译 | TypeScript Project References + `tsc -b` | M0 不引入应用打包器 |
| Schema | TypeBox | 同源生成 TypeScript 类型与 JSON Schema 2020-12 |
| 校验 | Ajv strict mode | 所有外部输入、持久化读取和 `--json` 边界执行校验 |
| SQLite | Node.js `node:sqlite` | 只允许 `store-sqlite` 直接依赖；M0 不使用 ORM |
| CLI | Commander 风格的分层命令 | CLI 库被限制在 `apps/cli`，不泄漏进 Kernel |
| 测试 | Vitest | 包内单元/契约测试，根目录保存跨模块场景测试 |

选择 `node:sqlite` 的原因是 Node.js 24 已直接提供同步 SQLite API、事务所需原语和备份能力，可以避免额外原生扩展的安装与打包问题。由于该 API 当前仍是 Release Candidate，所有调用必须封装在 `store-sqlite`；若后续兼容性不满足，只替换该适配包。

## 3. Monorepo 布局

```text
.
├─ apps/
│  └─ cli/
│     ├─ src/
│     └─ test/
├─ packages/
│  ├─ protocol/
│  │  ├─ src/
│  │  ├─ schemas/
│  │  └─ test/
│  ├─ store/
│  │  ├─ src/
│  │  └─ test/
│  ├─ kernel/
│  │  ├─ src/
│  │  └─ test/
│  └─ store-sqlite/
│     ├─ src/
│     ├─ migrations/
│     └─ test/
├─ tests/
│  └─ scenarios/
├─ docs/
└─ package.json
```

依赖只能沿以下方向发生：

```text
protocol ← store ← kernel ← cli
     ↑         ↑          ↖
     └─────────┴─ store-sqlite
```

准确解释：

- `protocol` 不依赖其他项目包；
- `store` 只依赖 `protocol`；
- `kernel` 依赖 `protocol` 与 `store`；
- `store-sqlite` 实现 `store`，依赖 `store` 与 `protocol`，不被 Kernel 反向引用；
- `cli` 是 Composition Root（装配根），负责创建 SQLite Store 并注入 Kernel；
- 包依赖检查进入 CI，禁止循环依赖和跨包内部路径导入。

## 4. Protocol 最小对象

M0 只实现首个纵向切片实际需要的对象 Schema，但保留 V1 既有命名和版本规则。

### 4.1 权威对象

- Project；
- Actor；
- Role；
- Assignment；
- Change。

### 4.2 不可变记录

- Command Receipt（命令回执）；
- Event；
- Transition Record；
- Outbox Message。

### 4.3 公共构件

- Internal ID；
- Display Key；
- Typed Object Reference；
- Source Descriptor；
- Command Envelope；
- Event Envelope；
- Domain Error；
- Schema Version、Revision、Event Sequence 与 UTC 时间语义。

每种对象独立使用 `schema_version`。Schema 构建时导出到 `packages/protocol/schemas/`，并用快照测试阻止未声明的协议变化。

## 5. 身份与展示编号

- Internal ID 使用 UUIDv7，作为全局稳定、不可变、无业务含义的主身份；
- Project、Actor、Change、Event、Command 等使用相同编码规则，但必须和 Object Type 一起形成 Typed Reference；
- Display Key 仅用于人类交互，M0 的 Change 使用项目内递增的 `CHG-0001` 形式；
- CLI 同时接受 Internal ID 和无歧义的 Display Key；
- 数据迁移和 Export/Import 永远以 Internal ID 为准，Display Key 可以重新展示但不能替代身份。

## 6. Kernel API

Kernel 暴露 Command 与 Query 两条明确路径：

```text
execute(CommandEnvelope) → CommandResult | DomainError
query(QueryRequest)       → ReadResult | DomainError
```

Command Handler 的固定流程：

1. 使用 Protocol Schema 校验 Envelope 与 Payload；
2. 规范化 Payload 并计算请求摘要；
3. 在事务内检查 `command_id` 幂等记录；
4. 加载目标聚合与当前 Revision；
5. 校验 `expected_revision`；
6. 运行纯领域函数，得到新状态、不可变记录和待发布 Event；
7. 原子保存 Current State、Transition、Event、Outbox 与 Command Receipt；
8. 提交后返回结果。

领域函数不得访问文件、SQLite、时钟或随机数。时间、ID 与当前 Actor 通过执行上下文注入，使测试可重复。

## 7. M0 Command 与 Query

### 7.1 Command

- `InitializeProject`；
- `CreateChange`；
- `PauseChange`；
- `ResumeChange`。

### 7.2 Query

- `GetProject`；
- `GetChange`；
- `ListChanges`；
- `GetProjectHealth`。

初始化 Project 时创建：

- 稳定 Project ID；
- 经用户确认的 Human Actor；
- Project Owner Role/Assignment；
- Solo Instance ID；
- 用户级 registry 中的可重建项目索引。

创建 Change 时，当前 Human Actor 默认成为唯一 Change Owner。Agent 在 M0 不作为正式 Runtime Actor 接入。

## 8. Change 的 M0 状态

M0 创建的 Change 主生命周期固定为 `Draft`。只实现运行状况 Overlay（叠加状态）：

```text
Active → Paused → Active
```

规则：

- 新 Change 为 `Draft + Active`；
- 暂停必须提供非空原因；
- 已暂停时再次暂停返回 `CHANGE_ALREADY_PAUSED`；
- 未暂停时恢复返回 `CHANGE_NOT_PAUSED`；
- Revision 不匹配返回 `REVISION_CONFLICT`；
- 每次成功变更生成 Transition Record 与领域 Event；
- 失败命令不修改 Current State，不增加 Event Sequence，也不写 Outbox。

## 9. 错误模型

所有错误使用稳定结构：

```json
{
  "code": "CHANGE_ALREADY_PAUSED",
  "message": "Change 已处于暂停状态",
  "category": "conflict",
  "retryable": false,
  "details": {},
  "correlation_id": "..."
}
```

错误类别至少包括：

- `validation`：Schema 或参数错误；
- `not_found`：目标不存在；
- `conflict`：Revision 或当前状态冲突；
- `forbidden`：Actor/Role/Policy 不允许；
- `storage`：本地持久化失败；
- `internal`：未预期错误，不能泄露数据库路径、SQL 或凭据。

CLI 根据类别映射稳定退出码；人类输出中文解释，`--json` 输出完整结构。错误码属于兼容性契约，修改需要显式迁移。

## 10. Store Port

`store` 定义逻辑端口，不暴露 SQL、连接对象或 SQLite 错误：

- Project/Identity/Change Repository；
- Event Ledger；
- Outbox Store；
- Command Receipt Store；
- Transaction/Unit of Work；
- Schema Migration 与 Health Query。

一次 Command 的所有写入必须位于同一个数据库事务。Kernel 不允许先写状态再补 Event，也不允许在事务提交前执行外部副作用。

## 11. SQLite 持久化

M0 数据表：

- `schema_migrations`；
- `projects`；
- `actors`；
- `roles`；
- `assignments`；
- `changes`；
- `transition_records`；
- `event_ledger`；
- `outbox_messages`；
- `command_receipts`。

对象表保留常用索引列和经 Schema 校验的规范 JSON Payload。不可变表只允许插入，不提供普通更新接口。

SQLite 打开后设置：

- `journal_mode = WAL`；
- `synchronous = FULL`；
- `foreign_keys = ON`；
- `busy_timeout = 5000`；
- 禁止动态扩展加载；
- 使用参数化语句，不拼接输入 SQL。

M0 写入量较低，优先选择更强的崩溃一致性而不是最大吞吐量。

## 12. 幂等、并发与 Outbox

### 12.1 幂等

- `command_id` 在 Project 内唯一；
- 首次执行保存规范请求摘要和完整 Command Result；
- 相同 `command_id`、相同摘要返回原结果，不重新执行；
- 相同 `command_id`、不同摘要返回 `COMMAND_ID_REUSED`。

### 12.2 乐观并发

- 修改已有聚合必须提供 `expected_revision`；
- 成功提交后 Revision 加一；
- 不匹配时返回当前 Revision，但不自动覆盖或重试业务命令。

### 12.3 Outbox

- Event 与对应 Outbox Message 在同一事务写入；
- M0 的投递器只验证 `pending → delivered`、失败重试和重启恢复；
- Claim Message 使用短 Lease，进程终止后可以重新领取；
- Event ID 是投递幂等键；
- 外部消费者尚未进入 M0，不能将 Outbox delivered 等同于业务处理完成。

## 13. 本地存储拓扑

Git 项目使用 Git Common Directory：

```text
.git/cimiloop/
├─ project.db
├─ objects/
├─ cache/
├─ staging/
├─ backups/
└─ instance.json
```

非 Git 项目使用根目录 `.cimiloop/`。CLI 初始化时明确提示该目录不得进入版本控制。

用户级应用数据目录包含 `registry.db`，只记录 Project ID、Repository 定位信息、最近打开时间与可用状态。它是可重建 Read Model，不能保存 Change 权威事实。

M0 创建目录边界，但只实际使用 `project.db` 与 `instance.json`；对象附件、缓存、Import/Export 和备份能力在后续里程碑实现。

## 14. CLI 契约

M0 命令：

```text
cimiloop init
cimiloop change create --title <title>
cimiloop change list
cimiloop change show <id-or-key>
cimiloop change pause <id-or-key> --reason <reason>
cimiloop change resume <id-or-key>
cimiloop doctor
```

共同参数：

- `--json`：输出 Schema 校验后的机器结果；
- `--command-id`：覆盖自动生成的幂等 ID；
- `--expected-revision`：修改命令的乐观并发条件；
- `--project-dir`：非当前目录或非 Git 场景下显式定位项目。

交互式 `cimiloop init` 读取 Git `user.name` 与 `user.email` 作为建议并请求确认。非交互方式必须显式提供 Owner 信息并使用 `--yes`，不能静默把 Agent 或系统账户登记为 Human Actor。

## 15. 测试策略

### 15.1 Protocol 测试

- Schema 快照；
- 合法/非法样例；
- JSON Schema 导出稳定性；
- Event 和 Command Envelope 兼容性。

### 15.2 Kernel 单元测试

- 创建 Draft Change；
- Active/Paused 合法转换；
- 重复暂停和错误恢复；
- Revision 冲突；
- 失败命令零写入；
- 固定时钟与固定 ID 下结果可重复。

### 15.3 Store 契约测试

同一组 Store Port 测试必须直接运行在临时 SQLite 文件上：

- 原子提交与回滚；
- Command Receipt 幂等；
- Event Sequence 连续；
- Current State 与最后 Event 一致；
- Outbox 重启恢复；
- Migration 可重复执行；
- 关闭并重新打开数据库后状态不变。

### 15.4 场景测试

- 从空目录执行完整 M0 CLI 流程；
- 同一 `command_id` 重放；
- 两个客户端使用相同 Revision 竞争更新；
- 在提交前注入故障，确认全部回滚；
- 在提交后、返回前注入故障，重试得到原结果；
- Outbox 领取后进程终止，Lease 到期后恢复投递。

## 16. 实施顺序

1. 建立 pnpm Workspace、TypeScript 严格配置、测试和依赖边界检查；
2. 实现 Protocol 公共构件、Project/Actor/Assignment/Change Schema；
3. 实现纯 Kernel 状态转换和错误模型；
4. 定义 Store Port 与共享契约测试；
5. 实现 SQLite Migration、事务、Event Ledger、Outbox 和 Command Receipt；
6. 实现 `cimiloop init` 与项目发现；
7. 实现 Change create/list/show/pause/resume；
8. 完成故障注入、重启恢复和端到端场景；
9. 生成 JSON Schema 制品与 M0 演示脚本；
10. 通过退出条件后冻结 M0，进入 M1。

## 17. M0 退出条件

- 可以初始化 Project 并创建、查询 Draft Change；
- 合法暂停/恢复成功，非法操作返回稳定错误和中文解释；
- 重复 Command 不重复写入；
- Revision 冲突不会丢失更新；
- 事务提交前故障不留下部分状态；
- 提交后响应丢失可以通过幂等重试恢复原结果；
- 重启后 Current State、Event Ledger 与 Outbox 保持一致；
- Kernel 不依赖 SQLite、CLI 或 Agent Runtime；
- 所有 `--json` 输入输出通过 Protocol Schema 校验；
- 文档、Schema、测试与演示行为一致。

满足以上条件后，M1 才开始引入真实 Contract、Risk、Profile、Decision、Gate、Plan 与 Knowledge Impact Assessment。
