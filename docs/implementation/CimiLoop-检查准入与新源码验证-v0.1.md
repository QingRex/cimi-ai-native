# CimiLoop 检查准入与新源码验证 v0.1

日期：2026-10-08，D-228，V1-09 续批。承接 [原 SDK 固定检查消费](CimiLoop-OpenCode固定检查工具消费-v0.1.md)。把检查定义和实际输入接入原生 Context / Run 固定关系，再由预约后的原运行安装目录。原完整 Runtime / 账户保管链及正向 Provider 资格在测试中仍构造；本批完成检查准入部分，不批准生产 Agent 或完整 S1。

## 准入先于运行身份

`PrepareRunContext` 的宿主准入发生在 Run ID、操作键和最终 Context 摘要产生之前。D-227 的运行目录包含这些身份，不能直接把整个目录摘要写回同一 Context 的准入凭据，否则形成递归摘要依赖。

本批先准备独立 `WorkspaceCheckInstallation`：原 OS 仓库目录身份、Node 字节和既有项目策略。仍使用同一不可覆盖的策略记录、128 个保留逻辑槽位和原 Node 配置，不重置历史容量。同步核对原 Node / 副本字节、策略原字节和目录 dev / inode；预约后安装时再次通过原 Windows 文件宿主核对实际根目录身份。

`LocalAgentCheckAdmission` 在 Context 准入阶段固定检查模板、原 Task / 定义 / Contract / Plan、WorkItem / 执行者 / 权限 / 预算、SourceSnapshot、实际 WorkspaceManifest 摘要及 Runtime / Skill Binding。它排除后续生成的 Context / Run ID，以及 Task 状态、修订和累计用量，保证正常预约后的当前事实不被误报为定义变化。

记录保存为版本化 `agent_host_admission` 内容引用，Context 原摘要包含这个引用。预约后以原 Context 摘要、Run ID、操作键和 Scope 生成 D-227 目录；目录与准入记录形成单向固定关系，没有伪造提前存在的 Run ID，也没有改写原 Context。

## 检查入口固定，来源来自实际快照

模板由可信组合器安装，不是模型参数。检查入口必须有固定内容摘要，其他固定依赖也可声明摘要；没有固定摘要的输入，从原 Context 的 WorkspaceManifest 内容引用取得实际摘要。来源必须在 WorkItem 范围内、实际存在、为有效 UTF-8 且不超过现有单文件 16 KiB 上限；缺失、越界或改写固定检查入口均拒绝。

模型无法提供未来修改的预期字节来形成正式检查输入。实现后的源码应先捕获为新的源码 / 工作区依据，准备新的验证 Context，再预约验证 Run。测试真实修改并提交源码，随后捕获新 SourceSnapshot 与 Context；SDK 只消费 `cimi_check`，不接收 replacement 参数或执行额外文件修改。验证输入摘要因此来自实际新源码，而不是 D-227 演练预设的替换内容。

如果来源在预约后再次变化，原目录保持不变。检查宿主的实际文件句柄读取会拒绝过期摘要，dispatch 前保存 not_started；不能用自动更新摘要、旧通过回执或新调用 ID 掩盖变化。当前独立只读 Context 的既有权限规则保持；这个检查模式不构成 Matt 独立评审或 Superpowers 真实方法调用。

## 检查准入保留原完整保管链

组合器必须提供原 Runtime 准入及当前保管链核验回调。检查记录保留原完整准入引用；当前工具核验重新读原记录、Node / 策略 / 模板及实际快照，再要求原完整保管链核验。原资格 / 账户 / 执行监督不能由“检查通过”替代，模块不安装默认成功回调或默认 Agent 入口。

完整 Runtime 组合器需把本模块的 `admit` / `validateTool` 与自身原 SDK / 工具 / 模型 / 账户记录核验一起接通，并在运行结果核验时保留组合准入及原完整准入之间的关系。模块不重写原 Run / Context 身份以迁就旧保管链接口，也不自报已有真实模型、费用或物理配额证明。测试中的这两种回调明确为构造端口。

`LocalAgentWorkspaceToolService.installAdmittedChecks` 从当前原生记录取得原输入与准入，安装时比较完整配方、Node 和策略。组合准入的 Run 拒绝旧的手工配方安装入口；不同模板或不同运行不能替换原配置。当前 Kernel 对撤销、当前角色 / 任务 / Binding / 预算和工具范围的复核继续存在，已准入记录的存在不代表仍获授权。

## 验证与边界

实际场景核对新源码提交、新 SourceSnapshot / Context / 预约、重新打开检查准备器后读取原记录、原 SDK 只调用检查、实际 Node 读取新源码并通过，以及 Task / Run / 预算不随工具输出自动推进。另覆盖旧 Context 拒绝预约、预约后来源变化不 dispatch、固定检查入口被改写、模板 / 原准入在预约前变化、未登记检查入口、原保管链失效、Human 撤销、原内容损坏和策略损坏。模板契约拒绝可执行输入、未知字段、路径别名和超界限制。

首轮扩大回归覆盖 20 文件 158 项，155 项通过；3 项失败发现跨包源码导入导致构建后的 CLI / 恢复子进程无法加载模块。修复为 Runtime 包导出，重新构建并验证 CLI 启动；最终重跑两处失败文件、两个新检查准入文件及工作台服务，共 5 文件 32 项。其余 15 文件使用首轮通过记录，不声称全部 158 项均在最终源码上重跑。最终源码、回归、初轮断言修正与审计见 [D-228 验证记录](../research/CimiLoop-检查准入与新源码验证-2026-10-08.json)。检查结果仍仅表示固定命令事实；原完整 Provider 资格 / 保管链与模型回复构造，不是生产模型或完整方法验收。Protocol 242 Schema、原生数据库格式 10、既有检查 / 文件回执和四个公共控制器保持；凭据读取 / 外部模型请求为 0，未升级用户库。

剩余：正式 Runtime 生命周期与完整准入 / SDK / 工具 / 账户保管链、实际模型 / 套餐 / 服务端上界及批准费用 / 账单、物理配额 / 历史容量 / 全恢复；Plan / Task 前 Human / Matt 澄清、真实技能与独立完整评审 / Superpowers 新鲜验证和行为对照；工作台正式 Agent 操作和真实普通 Change 到 ReadyForDelivery 的完整 S1 验收。旧缺登记和跨登录资源恢复的 Unknown 保持。五组目标均未完成。
