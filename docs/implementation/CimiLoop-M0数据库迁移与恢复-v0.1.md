# CimiLoop M0 数据库迁移与恢复 v0.1

> 日期：2026-10-07。对应 V1-02 迁移基础、V1-03 规划表、V1-04 格式 4 确认、V1-05 格式 5 任务 / 授权及 V1-06 格式 6 证据 / 评价记录、V1-07 格式 7 运行 / 交接记录及 V1-09 格式 8 Provider原生证据 / 评测的实际实现，当前开发任务仍以 [V1 实施基线](CimiLoop-V1可执行设计与实施计划-v0.1.md)为准。本文不表示用户现有项目已经升级。

## 支持范围

当前 SQLite 数据库格式为整数 `10`，领域协议为 `2.0.0`，各自演进。新项目直接创建格式10；已有格式1–9必须显式升级至10，正常Store和CLI不自动升级。较新数据库返回DATABASE_TOO_NEW，不尝试降级。

支持由原 M0 Kernel 生成的单项目数据库：一个初始化 Human Actor、一份 Project Owner Role 和 Assignment，以及 Draft Change、暂停 / 恢复事实、成功 Receipt 和事件投递 Outbox。结构、索引、当前对象、事件顺序、外键、Receipt 和 Outbox 不符合原 M0 时拒绝迁移，不能只改版本标记绕过检查。空的未初始化数据库、额外身份结构、未知状态或协议不在自动转换范围内。

格式 2 支持此前基础 / 责任治理版本的单项目库，包括 M0→2 保留的原 v1 历史和迁移来源。预检查核对已知表、索引、触发器、协议载荷与索引、当前对象与不可变成功回执 / 事件、角色及指派来源、连续聚合版本、计数器、Transition 和 Outbox 租约。不接受未实现的约定 / 计划 / 设置指针、非Draft状态或未知扩展；当前对象即使符合Schema，只要与历史事实不符也拒绝。迁移操作者须为当前有效 Human Project Owner。

格式 3 支持此前设置 / 规划版本，在上述检查之外核对不可变设置版本及前驱链、当前设置指针、目标版本当前状态、规划调整前后和对应回执 / 事件。已有配置、目标版本和规划历史原样保留；尚未实现的正式约定 / 计划及非Draft状态仍拒绝。不提供通过删除新表、改写标记或伪造旧事实来降级的产品入口。

格式 4 支持真实确认版本与开工状态：核对不可变候选 / 风险 / 请求 / 决定 / 正式版本、事件与精确回执，区分不增加 Change Revision 的记录动作，验证正式指针和生命周期前后。保留 IntentReady / Executing / 暂停及全部确认事实；未知后续状态或历史不符时拒绝。增加空任务 / 授权表，不生成任务、授权或运行。

格式 5 支持真实持久 Task / TaskDefinition、具体授权、常规授权版本及 WorkItem 创建 / 撤销。在上述检查之外核对执行对象连续版本、不可变记录与事件 / 成功回执一致、常规授权前驱及项目基准；拒绝超出当时实现的 InProgress / Satisfied Task、Active / Closed WorkItem 和伪造历史。逐项保留原任务、授权、用量及撤销事实，新增空 verification_records，不生成满足、运行或评价。工程测试中重建旧布局仅用于已知格式迁移回归，不是产品降级入口。

格式 6 支持真实固定源码、原始人工证据、需求集 / Context / 评价、任务满足 / WorkItem关闭、ReadyForDelivery、批准条件核验、证据失效处置及高风险专业决定。预检查逐项核对验证记录与事件 / 回执来源、记录动作与可变对象版本、正式指针和实际生命周期；不接受只有Schema正确但与历史不符的记录，也拒绝旧格式未实现的Run字段。升级新增空run_objects / run_records，不生成运行、用量或交接事实。

格式7支持真实Human运行、Task累计用量、原始观测与取消未知、交接接续及候选Provider登记。预检查核对冻结格式7布局、连续Run / Task / WorkItem版本、预约 / 观测 / 用量 / 交接来源和事件 / 回执一致性，ProviderRegistered与Descriptor原文相符；Schema合法但运行事实被改写时拒绝。迁移保留全部原字节与运行状态，仅新增空provider_assessment_records及严格项目 / Descriptor关联、不可变写入保护，不补造Provider评测或批准。

格式8支持实际原生Runtime Provider证据、技术 / 受控执行评测及探针批准，也保留D-210的Skill候选。预检查冻结旧Runtime证据用途及规则版本，核对Descriptor摘要、Human来源、评测引用、实际批准指派、事件和回执。格式9只增加明确的技能记录分支及种类守卫，既有Runtime和Human事实不转换；不能把新Skill观测写入旧库再改标记冒充旧历史。

格式9预检查同时核对原生Runtime / Skill证据种类、评测规则、准确事件 / 回执、Skill批准的固定Runtime与Human批准依据。格式10增加独立Agent Context / Run / 原始结果分支和关系写守卫；迁移保留全部旧记录、累计用量、未知状态及原始内容，不生成Agent事实或正式Task批准。格式7–9运行用冻结Human Schema核对，不能通过改标记冒充旧Agent历史。见[Agent上下文与运行固定关系](CimiLoop-Agent上下文与运行固定关系-v0.1.md)。

`instance.json` 仍是版本 1 的本地定位文件，内部稳定 ID 不变；它的版本不等于领域协议。Protocol 根入口继续保留冻结 v1，当前 Kernel、Store 和 CLI 显式使用 `/v2`。Kernel / Store / SQLite 的 `/v1` 入口用于旧实现回归及迁移样本，不能打开新格式；新库的写入触发器也拒绝 v1 JSON。

## 操作入口

使用 Node.js 24.15.0 和 pnpm 12.4.2，先构建，再检查指定项目：

```powershell
pnpm build
pnpm cimiloop --project-dir "D:/path/to/project" --json migrate --check
```

`--check`在只读事务中检查格式1–9和转换前提，返回严格MigrationReport，含源 / 目标格式、是否升级及对象 / 事件 / Receipt / Outbox数量。它不创建备份或改写对象；格式10返回无需升级。

执行升级前停止该项目的外部写入和投递 Worker，等待尚有效的 Outbox 租约结束，然后显式执行：

```powershell
pnpm cimiloop --project-dir "D:/path/to/project" --json migrate
pnpm cimiloop --project-dir "D:/path/to/project" --json doctor
```

操作者使用原 `instance.json` 中的初始化 Owner ID，并核对原初始化事件和 Assignment。升级报告给出迁移 ID、一致性备份路径与 SHA-256 摘要。省略 `--json` 时显示中文说明。已经完成升级后再次执行不会追加迁移事件或备份。

## 停写、备份与原子提交

1. 在数据目录独占创建 `.migration.lock`，记录 PID、开始时间和数据库绝对路径。数据库较新或格式未知时，在创建锁和写连接之前拒绝操作。
2. 用 `BEGIN IMMEDIATE` 持有 SQLite 写锁，贯穿预检查、备份和升级。已有写事务使升级失败；锁持有期间其他连接不能提交写入。有效投递租约使迁移被拒绝。
3. 单独的只读连接调用 Node `node:sqlite` 的一致性 `backup()`，得到包含已提交 WAL 数据的独立数据库。不能用文件复制代替活动数据库备份。
4. 在 `backups/<迁移 ID>/` 保存 `project.db`、`manifest.json`，以及 `data/` 下的其他数据目录文件。清单包含相对路径、大小和 SHA-256；数据库的 WAL/SHM、备份目录和迁移锁不作为普通内容文件复制。拒绝符号链接及无法完整备份的文件类型。备份前后、提交前核对源内容；备份数据库再次通过对应源格式的预检查。
5. 在同一写事务内安装缺失的格式表和保护，格式1另转换 Current State、扩展 Outbox并保存来源，格式2–9保留原业务数据；追加迁移事实和格式标记，执行完整性与外键检查后提交。检查、备份或转换失败就回滚；已经生成的备份保留。

SQLite 写锁和文件摘要检查不能代替外部进程的停写安排。当前没有自动停止 / 重启外部 Worker 的管理服务，调用方负责让内容目录及投递过程保持静止。

## 保留和转换的事实

| 数据 | 升级行为 |
|---|---|
| 格式 1 的 Project / Actor / Role / Assignment | 保留 ID、Revision 和创建时间；补入当前对象元数据、项目归属及结构化 Scope。初始化 Assignment 的 `granted_by` 来自原初始化 Actor / Event，不凭空生成负责人 |
| 格式 1 的 Change | 保留 ID、展示键、Owner、Draft、运行状态、暂停原因、时间和 Revision；新增 `kind=requirement`、`priority=0`；需求负责人、约定、计划与设置保持未配置 |
| 格式2–7的所有当前对象及历史 | 逐项原样保留，不重复转换 v2，也不重写保留的 v1 历史与旧迁移来源 |
| 设置版本 / 目标版本表 | 格式1 / 2新建空表及严格写入保护，格式3–7原样保留；设置版本不可变、目标版本带 CAS；不默认生成容量配置或规划 |
| intent_records | 格式1 / 2 / 3新建空表，格式4–7逐项原样保留候选、风险、决定、正式版本及生命周期；不生成虚构批准 |
| execution_objects / execution_records | 格式1–4新建空任务 / 授权表；格式5–7逐项原样保留任务、WorkItem、常规授权 / 前驱及撤销、具体授权、累计用量；不补造授权或用量 |
| verification_records | 格式1–5新建空的严格不可变证据 / 评价表，格式6 / 7原样保留；不补造源码、报告、评价上下文、任务满足或集成准入 |
| run_objects / run_records | 格式1–6新增空表；格式7逐项保留Run、预约 / 观测 / 交接接续及累计用量，不补造实际执行或成功 |
| provider_assessment_records | 格式1–7新增空Provider原生证据 / 评测表及不可变保护；不生成评测、Binding批准或执行资格 |
| Event / Transition / 成功 Receipt | 原 JSON、v1 标记和请求摘要不改写；旧成功结果本来没有版本字段，也不补造；通过版本化读取保留原形状 |
| ProjectCounter | Change 编号不重置；Event Sequence 接续旧序列，追加一条 `ProjectMigrated`，不改变业务对象 Revision |
| Outbox | 格式1保留原投递状态、尝试次数和时间，新增legacy效应及原事件目标引用，唯一性改为`(event_id, effect_key)`；格式2–7逐项原样保留；不生成部署动作 |
| 迁移来源 | `migration_runs` 保存操作者、备份及清单；`migration_origins` 保存每个转换对象的原 JSON、原版本和摘要；均不可改写 |

新格式 Store 具有严格对象读取、Change CAS、不可变 Provider 元数据 / 确认记录与 v2 Receipt 追加入口。新 Receipt 可保存 v2 成功或领域错误，Kernel 当前仍只保存成功结果；拒绝回执的业务处理由后续任务完善。Provider 元数据写入不代表 Provider 已评测、绑定权限已核对或实际调用可用。

查询在 SQLite 读快照内同时取得数据和 `as_of_event_sequence`。Outbox 确认 / 释放需要当前领取的尝试次数和租约截止时间，过期 Worker 不能确认已被另一 Worker 重新领取的消息。

## 旧命令兼容

Kernel 先按原协议验证命令、核对可信入口绑定的实际调用身份并计算原请求摘要，再查 Receipt。相同 `command_id` / 摘要返回原结果，不先补入 v2 字段、不重新执行，也不追加 Event / Outbox；同 ID 不同内容返回 `COMMAND_ID_REUSED`。没有绑定或命令身份与绑定不符，即使命中旧回执也拒绝。

尚未处理的合法 v1 基础命令转换为 v2 执行，title-only 默认和 Draft 暂停 / 恢复语义保留。当前仅允许本地 Human 来源、已登记 Actor 和有效项目范围 Project Owner 指派；暂停 / 恢复还核对原 Change Owner。Agent 来源不能借用现有 Human Owner 执行这些基础命令。

CLI 在显式 `--command-id` 命中旧 Receipt 时沿用旧协议语义；暂停 / 恢复未显式传 Revision 时，使用原成功结果对应的期望 Revision，使重放不受当前 Revision 影响。更改参数仍会被摘要检查拒绝。

V1-03 已增加可信 Caller、角色范围与期限、授予 / 结束 / 原子移交及治理CLI，以及设置、规划与容量基础；V1-04接通真实Contract / Plan确认及正向开工。原生v2暂停 / 恢复要求显式Change Owner指派；旧Change若仅有负责人指针，须新增当前指派或执行原子移交，不回溯伪造历史授权。具体命令见[责任治理](CimiLoop责任治理与身份入口-v0.1.md)、[设置、规划与容量](CimiLoop项目设置规划与容量-v0.1.md)及[确认与开工](CimiLoop约定计划确认与开工-v0.1.md)。运行、执行中恢复和发布仍在后续任务，不把预留状态当成已经可执行。

## 失败与恢复

- `MIGRATION_REQUIRED`：正常入口发现格式1–7；先运行检查再显式升级。
- `DATABASE_TOO_NEW`：当前程序不支持该格式；使用匹配版本，不改标记尝试降级。
- `MIGRATION_UNSAFE`：未知 / 不一致数据、有效租约、写锁冲突、已有迁移锁、文件变化或备份 / 转换失败。先处理报告指出的原因，不能跳过检查。

进程突然退出时 SQLite 恢复未提交事务，源库保持原格式1–7，已经完成的备份保留；`.migration.lock` 可能残留。读取锁中的 PID 和开始时间，确认对应进程及项目 Worker 已停止后，才由操作者处理残留锁再重试。程序不按锁文件年龄自动夺取写权。

若尚未产生升级后的新业务事实或外部副作用，可停写并封存当前数据目录，核对备份摘要，将一致性备份数据库与 `data/` 中的文件恢复到清单对应位置，再用匹配版本检查。当前库的 WAL/SHM 随封存目录保留，不能与备份数据库混用；备份目录本身也保留。

产生新业务事实或外部副作用后，先保存这些事实并评估恢复办法；当前没有自动降级、覆盖新历史或外部动作补偿入口。恢复操作需要针对实际数据单独安排，不能把测试样本上的成功恢复视为生产恢复已执行。
